## Internationalization (i18n)

Sveltia CMS comes with first-class support for internationalization, allowing editors to manage content in multiple languages seamlessly. This guide covers the configuration options and best practices for setting up i18n in your Sveltia CMS projects.

**Note for Netlify/Decap CMS users**

All i18n issues in Netlify/Decap CMS have been resolved in Sveltia CMS. The [limitations](https://decapcms.org/docs/i18n/#limitations) mentioned in their documentation do not apply to Sveltia CMS.

**Why i18n is at the core of Sveltia CMS**

Sveltia CMS was originally built for [@kyoshino](https://github.com/kyoshino)’s Japanese clients, who needed a CMS that could handle multilingual content efficiently. The maintainer is a former long-time localizer for [Mozilla](https://www.mozilla.org/) and lives in the [most diverse city in the world](https://en.wikipedia.org/wiki/Toronto), where 150+ languages are spoken.

As a result, i18n support is deeply integrated into Sveltia CMS from the ground up, making it a powerful choice for projects that require multilingual content management.

### Examples

See our [Showcase](https://sveltiacms.app/en/showcase?feature=i18n) for examples of websites using Sveltia CMS with i18n support. Most of them come with a link to the source code, which can be a great resource for learning how to implement i18n in your own projects.

### Configuration

To use i18n support in your Sveltia CMS project, you need to define the `i18n` option in the top-level, collection-level and field-level configurations. For a [file collection](https://sveltiacms.app/en/docs/collections/files), file-level configuration is also required. See [Configuration Options](https://sveltiacms.app/en/docs/i18n/options) for what each level accepts.

The below example demonstrates how to set up i18n at all levels for an [entry collection](https://sveltiacms.app/en/docs/collections/entries):

```yaml [YAML]
i18n:
  structure: multiple_folders
  locales: [en, de, fr]

collections:
  - name: posts
    label: Blog Posts
    folder: /content/posts
    i18n: true
    fields:
      - name: title
        label: Title
        widget: string
        i18n: true
      - name: date
        label: Date
        widget: datetime
        i18n: duplicate
      - name: body
        label: Body
        widget: richtext
        i18n: true
```

```toml [TOML]
[i18n]
structure = "multiple_folders"
locales = ["en", "de", "fr"]

[[collections]]
name = "posts"
label = "Blog Posts"
folder = "/content/posts"

[[collections.fields]]

label = "Title"
widget = "string"
i18n = true

[[collections.fields]]
name = "date"
label = "Date"
widget = "datetime"
i18n = "duplicate"

[[collections.fields]]
```

Each level only takes effect on top of the one above it. If you leave one out, the content stays monolingual, with nothing to edit in the other locales. To catch this mistake early, Sveltia CMS reports the following as [configuration errors](https://sveltiacms.app/en/docs/config-basics#runtime-validation) on the login screen:

- The top-level `i18n` option is defined, but none of the collections or singletons have the `i18n` option.
- An entry collection has the `i18n` option, but none of its fields have `i18n: true` (or `translate`) or `i18n: duplicate`.
- A file collection has the `i18n` option, but none of its files have the `i18n` option.
- A collection file or singleton has the `i18n` option, but none of its fields have `i18n: true` (or `translate`) or `i18n: duplicate`.

A localized field nested in a List or Object field, or in a variable type, counts as well, and so do the fields of an entry collection’s [index file](https://sveltiacms.app/en/docs/collections/entries/listings#managing-hugo-s-special-index-file). Collections that don’t need translations can simply leave out the `i18n` option, so you can enable i18n for some collections only.

### Other I18n Features

Sveltia CMS embeds i18n support everywhere in the configuration and UI. Here are some additional features that enhance the multilingual content management experience.

- The [`summary` entry collection option](https://sveltiacms.app/en/docs/collections/entries/listings#summaries) supports the `{{locales}}` template tag to show enabled entry locales in the entry list.
- The [`default` Hidden field option](https://sveltiacms.app/en/docs/fields/hidden#default) supports the `{{locale}}` template tag to embed the locale code in an entry.
- The [`value_field` Relation field option](https://sveltiacms.app/en/docs/fields/relation#value-field) supports locale prefixes like `{{locale}}/{{slug}}`, which will be replaced with the current locale for i18n support in Astro. ([Discussion](https://github.com/sveltia/sveltia-cms/discussions/302))
- The [`commit_messages` backend option](https://sveltiacms.app/en/docs/backends#localizing-commit-messages) lets you localize commit messages by replacing words like “Create”, “Update” and “Delete” in the templates with words in your team’s language.
- The Content Editor can be [linked to a specific locale](https://sveltiacms.app/en/docs/ui/content-editor#editor-pane-locale) using a URL query parameter.

### Translating Content

Sveltia CMS provides a built-in mechanism for managing content translations. When a user creates or edits an entry in one locale, they can easily switch to another locale and provide the translated content. The CMS automatically links the translations together based on the i18n configuration.

Adding or updating translations can be done directly in the Content Editor. When viewing an entry, users can use the locale switcher in the top-right corner to switch between locales. If a translation for the selected locale does not exist, an option to create a new translation is shown.

When creating a new translation, Sveltia CMS will pre-fill the fields with the content from the default locale, allowing the user to modify only the necessary parts for the translation. This streamlines the translation process and ensures consistency across different language versions of your content.

## I18n Configuration Options

The `i18n` option can be defined at the top level of your configuration, on a collection, on a file in a [file collection](https://sveltiacms.app/en/docs/collections/files) and on individual fields. This page explains what each level accepts. For a complete example that sets up all levels at once, see the [Internationalization overview](https://sveltiacms.app/en/docs/i18n#configuration).

### Top-Level Configuration

Let’s start by defining the `i18n` option at the top level of your configuration. The `i18n` option accepts the following properties:

```yaml [YAML]
i18n:
  structure: multiple_folders
  locales: [en, de, fr]
```

```toml [TOML]
[i18n]
structure = "multiple_folders"
locales = ["en", "de", "fr"]
```

```json [JSON]
{
  "i18n": {
    "structure": "multiple_folders",
    "locales": ["en", "de", "fr"]
  }
}
```

```js [JavaScript]
{
  i18n: {
    structure: "multiple_folders",
    locales: ["en", "de", "fr"],
  },
}
```

- `structure`: (optional) Defines how localized content is stored. Default: `single_file`. See [Content Structures](https://sveltiacms.app/en/docs/i18n/structures) for the available options. An entry collection can instead put the `{{locale}}` placeholder in its `folder` option to say where the locale folder goes, as in `content/{{locale}}/posts`. See [Custom Locale Folder Placement](https://sveltiacms.app/en/docs/i18n/structures#custom-locale-folder-placement).
- `locales`: An array of locale codes representing the supported languages.
- `default_locale`: (optional) Explicitly sets the default locale. If not provided, the first locale in the `locales` array is used.
- `initial_locales`: (optional) Locales to be enabled when users create a new entry draft. Accepts a list of locale codes, `default` (default locale only) or `all` (all locales). When defined, users can enable or disable non-default locales in the Content Editor. See [Disabling Non-Default Locale Content](#disabling-non-default-locale-content) below.
- `omit_default_locale_from_file_path`: (optional) When using a structure that creates separate files for each locale (e.g. `multiple_files`), setting this option to `true` will omit the locale code from the file path for the default locale. It also applies to file collections whose `file` path includes the `{{locale}}` placeholder. This is useful for frameworks like [Zola](https://www.getzola.org/documentation/content/multilingual/) that expect the default locale to have a specific filename. See [Where the Placeholder Can Be Omitted](https://sveltiacms.app/en/docs/i18n/structures#where-the-placeholder-can-be-omitted) for the positions where the locale can be removed.
- `omit_default_locale_from_preview_path`: (optional) When set to `true`, the preview URL for the default locale will not include the locale code. This is useful for frameworks that expect the default locale to be served at the root path. The placeholder is removed in the [same positions](https://sveltiacms.app/en/docs/i18n/structures#where-the-placeholder-can-be-omitted) as with `omit_default_locale_from_file_path`, so `/{{locale}}/posts/{{slug}}` becomes `/posts/{{slug}}` and `/{{locale}}` becomes `/`. In any other position, the locale is kept.

**Deprecation Notice**

The `omit_default_locale_from_filename` option is deprecated and will be removed in Sveltia CMS v1.0.0. Use `omit_default_locale_from_file_path` instead. The old option is simply an alias of the new one, which takes precedence if both are defined.

#### Disabling Non-Default Locale Content

Developers can specify locales to be enabled by default when users create a new entry draft, using the `initial_locales` i18n option, which accepts a locale list, `default` (default locale only) or `all` (all locales).

The default locale is always enabled, even if it’s excluded from `initial_locales`, while other locales can be enabled or disabled by users in the Content Editor through the three-dot menu in the top-right corner, if this i18n option is defined.

The following example disables German by default, but users can manually enable it if needed. Users can also disable French, which is enabled by default.

```yaml [YAML]
i18n:
  structure: multiple_files
  locales: [en, fr, de]
  default_locale: en
  initial_locales: [en, fr]
```

```toml [TOML]
[i18n]
structure = "multiple_files"
locales = ["en", "fr", "de"]
default_locale = "en"
initial_locales = ["en", "fr"]
```

```json [JSON]
{
  "i18n": {
    "structure": "multiple_files",
    "locales": ["en", "fr", "de"],
    "default_locale": "en",
    "initial_locales": ["en", "fr"]
  }
}
```

```js [JavaScript]
{
  i18n: {
    structure: "multiple_files",
    locales: ["en", "fr", "de"],
    default_locale: "en",
    initial_locales: ["en", "fr"],
  },
}
```

**Deprecation Notice**

The `save_all_locales` option has been deprecated in favor of the more flexible `initial_locales` option and will be removed in Sveltia CMS v1.0.0. If you are upgrading from an older version, update your configuration accordingly:

- `save_all_locales: false` is equivalent to `initial_locales: all`.
- `save_all_locales: true` is equivalent to `initial_locales` being omitted (all locales enabled by default).

### Collection-Level Configuration

You can opt into i18n for a specific collection by setting the `i18n` option to `true`. This will use the top-level i18n configuration for that collection.

```yaml [YAML]{3}
collections:
  - name: posts
    i18n: true
```

```toml [TOML]{3}
[[collections]]
name = "posts"
i18n = true
```

```json [JSON]{5}
{

    {

    }
  ]
}
```

```js [JavaScript]{5}
      name: "posts",
      i18n: true,
    },
  ],
```

### Field-Level Configuration

Each field can be localized individually by setting the `i18n` option. The `i18n` option for fields accepts the following values:

- `true`
  - The field can be edited separately for each locale.
  - The values are stored separately for each locale.
- `false` (default)
  - The field can only be edited in the default locale.
  - The field is hidden in non-default locales.
  - Only the default locale’s value is stored.
- `duplicate`
  - The field can only be edited in the default locale.
  - The field is read-only in non-default locales, displaying the default locale’s value.
  - The same value is stored for all locales.
- `sync`
  - The field can be edited in every locale.
  - A change made in any locale is copied to the other locales. See [Keeping Values in Sync](#keeping-values-in-sync) for details.
  - The same value is stored for all locales.
- `duplicate_if_empty`
  - The field can be edited separately for each locale.
  - The default locale’s value is copied to non-default locales where the field is empty. See [Filling in Empty Values](#filling-in-empty-values) for details.
  - The values are stored separately for each locale.

**Legacy option values**

For backward compatibility with Netlify/Decap CMS, Sveltia CMS also supports `translate` and `none` values for the field-level `i18n` option, which are equivalent to `true` and `false`, respectively.

Here’s how the `i18n` option behaves for different field types:

- The [Hidden field type](https://sveltiacms.app/en/docs/fields/hidden) does not have a visible UI representation, but you’ll still need to set the `i18n` option to `true`, `duplicate` or `sync` to store values in non-default locales.
- The complex [List field type](https://sveltiacms.app/en/docs/fields/list):
  - `true` lets each locale have its own items, which can be added, removed and reordered separately. A subfield only becomes editable in the other locales with its own `i18n: true` option; a subfield without the option is hidden there. If no subfield has the option, items can only be added in the default locale.
  - `duplicate` makes all subfields duplicate. When the user adds, reorders or removes list items in the default locale, the same changes are reflected in other locales, where the items are shown read-only and can’t be added, removed or reordered. Subfields can be configured with their own `i18n` options.
  - `sync` keeps all subfields in sync. List items can be added, removed and reordered in any locale, and the same changes are reflected in the other locales. Subfields can be configured with their own `i18n` options.
- The [Object field type](https://sveltiacms.app/en/docs/fields/object):
  - `true` lets the object appear in the other locales. A subfield only becomes editable there with its own `i18n: true` option; a subfield without the option is hidden in the other locales.
  - `duplicate` makes all subfields duplicate, and they are shown read-only in other locales. Subfields can be configured with their own `i18n` options.
  - `sync` keeps all subfields in sync, and they can be edited in every locale. Subfields can be configured with their own `i18n` options.
- The [KeyValue field type](https://sveltiacms.app/en/docs/fields/keyvalue) additionally accepts `duplicate_keys`, which makes the keys duplicate — they are copied from the default locale, in the same order, and read-only in non-default locales — while the values can be edited separately for each locale.
- `duplicate_if_empty` is only available for the fields that hold a single, simple value: [Code](https://sveltiacms.app/en/docs/fields/code), [DateTime](https://sveltiacms.app/en/docs/fields/datetime), [File](https://sveltiacms.app/en/docs/fields/file), [Image](https://sveltiacms.app/en/docs/fields/image), [Number](https://sveltiacms.app/en/docs/fields/number), [Relation](https://sveltiacms.app/en/docs/fields/relation), [RichText](https://sveltiacms.app/en/docs/fields/richtext), [Select](https://sveltiacms.app/en/docs/fields/select), [String](https://sveltiacms.app/en/docs/fields/string) and [Text](https://sveltiacms.app/en/docs/fields/text). A File, Image, Relation or Select field that accepts multiple values works like one with `i18n: true`, and the CMS warns about it.


#### Filling in Empty Values

The `duplicate_if_empty` option is useful for a value that is usually the same in every locale, but sometimes needs a localized version. Examples include a banner image with text that hasn’t been localized yet, or a product name that is only translated in some markets.

Unlike `duplicate`, the field can be edited in every locale. Unlike `true`, a non-default locale doesn’t start empty:

- When an entry is opened, a non-default locale where the field is missing or empty gets the default locale’s value. This doesn’t count as a change, so the Save button stays disabled.
- When a locale is enabled for an existing entry, it gets the default locale’s value.
- As the user edits the field in the default locale, the change is copied to the non-default locales where the field is empty or still holds the default locale’s previous value. This way, a locale that follows the default locale stays in sync as the user types. A locale that has a value of its own is left alone. Reverting the change in the default locale restores the value in the locales that followed it.
- Values are only copied from the default locale to the other locales, never the other way around.
- Clearing the field in a non-default locale leaves it empty for now, but the next change in the default locale, or the next time the entry is opened, fills it in again. Clearing or restoring the field in the default locale with the field options menu doesn’t change the other locales.
- In a List field with `i18n: true`, a subfield with `duplicate_if_empty` makes the items paired across locales, as a subfield with `duplicate` or `sync` does. Items are added, removed and reordered in the default locale, and the same changes are reflected in the other locales. The values are therefore copied to the matching item.
- Translating all the fields of a locale at once also translates the fields that still hold the default locale’s value.
- The field is validated in every locale, just like a field with `i18n: true`.

In the following example, the `image` field takes the English image in every locale until a localized image is selected:

```yaml [YAML]{5}
fields:
  - name: image
    label: Banner Image
    widget: image
    i18n: duplicate_if_empty
```

```toml [TOML]{5}
[[fields]]
label = "Banner Image"
name = "image"
widget = "image"
i18n = "duplicate_if_empty"
```

```json [JSON]{7}
{
  "fields": [
    {
      "label": "Banner Image",
      "name": "image",
      "widget": "image",
      "i18n": "duplicate_if_empty"
    }
  ]
}
```

```js [JavaScript]{7}
{
  fields: [
    {
      label: "Banner Image",
      name: "image",
      widget: "image",
      i18n: "duplicate_if_empty",
    },
  ],
}
```

#### Keeping Values in Sync

The `sync` option is useful for a value that must be the same in every locale, but that editors may want to change while working on any locale, such as a product price, an event date or a link. With `duplicate`, the field is read-only outside the default locale, so an editor working on a translation has to switch back to the default locale to change it.

As with `duplicate`, the same value is stored for all locales. Unlike `duplicate`, the field can be edited in every locale:

- A change made in any locale is copied to the other locales as the user types. A Relation field value with a locale prefix, like `{{locale}}/{{slug}}`, and a DateTime field value with the `localize_format` option are converted for each locale.
- When an entry is opened, a non-default locale where the field is missing gets the default locale’s value. A value that differs between locales, for example because a file was edited outside the CMS, is left as is until the field is next changed in any locale.
- When a locale is enabled for an existing entry, it gets the default locale’s value.
- Clearing, restoring or reverting the field with the field options menu in any locale does the same in every locale. Reverting all the changes to the entry restores each locale’s own original value.
- A List field with `sync` lets the user add, remove and reorder items in any locale, and the same changes are reflected in the other locales. In a List field with `i18n: true`, a subfield with `sync` makes the items paired across locales, as a subfield with `duplicate` does. Items are then added, removed and reordered in the default locale only.
- The field is validated in every locale, so an error is shown in whichever locale the user is editing.
- The field is never translated or copied from another locale with the field options menu, since it already holds the same value everywhere.
- A [Compute field](https://sveltiacms.app/en/docs/fields/compute) with `sync` is computed from the default locale’s values, and the result is copied to the other locales.
- In a field of a [rich text editor component](https://sveltiacms.app/en/docs/fields/richtext#editor-components), `sync` works like `true`, because the component’s values are stored in each locale’s text.

In the following example, the `price` field can be changed in any locale, while every locale keeps the same price:

```yaml [YAML]{5}
fields:
  - name: price
    label: Price
    widget: number
    i18n: sync
```

```toml [TOML]{5}
[[fields]]
label = "Price"
name = "price"
widget = "number"
i18n = "sync"
```

```json [JSON]{7}
{
  "fields": [
    {
      "label": "Price",
      "name": "price",
      "widget": "number",
      "i18n": "sync"
    }
  ]
}
```

```js [JavaScript]{7}
{
  fields: [
    {
      label: "Price",
      name: "price",
      widget: "number",
      i18n: "sync",
    },
  ],
}
```

### Localized Field Options

A field’s label, help text and default value can be given for each locale with the following options, keyed by locale code. Each one takes precedence over its counterpart without the `_localized` suffix, which remains the fallback for the locales not listed:

- `label_localized`: Label of the field. Also available for a [variable type](https://sveltiacms.app/en/docs/fields/list#variable-type) of a List or Object field.
- `hint_localized`: [Hint](https://sveltiacms.app/en/docs/fields#common-options) of the field. Also available for a variable type.
- `label_singular_localized`: Singular label of a [List](https://sveltiacms.app/en/docs/fields/list) or [KeyValue](https://sveltiacms.app/en/docs/fields/keyvalue) field, shown on the Add button.
- `default_localized`: Default value of the field, in the same format as the `default` option of the field type.

There are separate options for this rather than letting `label` or `default` take an object, because the `default` option of some field types, such as Object, KeyValue and Code, is already an object, so the two couldn’t be told apart.

In the following example, an English and German site has a list of categories with labels and default values in both languages:

```yaml [YAML]{4-5,9-10}
fields:
  - name: categories
    label: Categories
    label_localized:
      de: Kategorien
    widget: list
    i18n: true
    default: [car repair, tuning]
    default_localized:
      de: [Autoreparatur, Tuning]
```

```toml [TOML]
[[fields]]
name = "categories"
label = "Categories"
label_localized = { de = "Kategorien" }
widget = "list"
i18n = true
default = ["car repair", "tuning"]
default_localized = { de = ["Autoreparatur", "Tuning"] }
```

```json [JSON]
{
  "fields": [
    {
      "name": "categories",
      "label": "Categories",
      "label_localized": { "de": "Kategorien" },
      "widget": "list",
      "i18n": true,
      "default": ["car repair", "tuning"],
      "default_localized": { "de": ["Autoreparatur", "Tuning"] }
    }
  ]
}
```

```js [JavaScript]
{
  fields: [
    {
      name: "categories",
      label: "Categories",
      label_localized: { de: "Kategorien" },
      widget: "list",
      i18n: true,
      default: ["car repair", "tuning"],
      default_localized: { de: ["Autoreparatur", "Tuning"] },
    },
  ],
}
```

How a localized value is picked depends on what it is:

- A label or hint in the Content Editor follows the locale of the pane, so the German pane shows German labels.

  Some places have no content locale: the entry list, the sort and filter menus, the table and bulk edit views, and a collection without i18n. There, the label for the user’s UI locale is used instead, matched by language, e.g. `de` for German (Austria). If neither is found, the label or hint without the suffix is shown. This means `label_localized` can also be used to translate the editor UI for a team working in a language other than the content’s.

- A default value is content, so it only follows the content locale. It only has an effect for a field with `i18n: true`, which has a value of its own in each locale. A field with `i18n: duplicate` or `i18n: sync` takes the default locale’s value in every locale, because it holds the same value everywhere. A value for a locale that isn’t configured, or the option in a collection without i18n, is never used, and the CMS warns about it.

Hardcoding default values that may change later, such as categories, is not always a good idea, though. If the categories are likely to be renamed or added, consider creating a separate collection for them and referring to it with a [Relation field](https://sveltiacms.app/en/docs/fields/relation).

## Translation Services

Sveltia CMS comes with a handy translation API integration for enhanced [i18n support](https://sveltiacms.app/en/docs/i18n). With the help of AI, any text field can be translated from another locale without leaving the Content Editor, making it easier to manage multilingual content.

### Supported Services

Currently, the following services are supported:

- Neural Machine Translation (NMT)
  - Google: [Cloud Translation](https://cloud.google.com/translate)
- Large Language Models (LLMs)
  - Anthropic: [Claude Haiku 5.5](https://www.anthropic.com/claude/haiku)
  - DeepSeek: [DeepSeek-V4.1-Flash](https://api-docs.deepseek.com/news/news260910)
  - Google: [Gemini 3.5 Flash-Lite](https://ai.google.dev/gemini-api/docs/models/gemini-3.5-flash-lite)
  - Mistral AI: [Mistral Small 4](https://docs.mistral.ai/models/model-cards/mistral-small-4-0-26-03)
  - OpenAI: [GPT-6 Luna](https://developers.openai.com/api/docs/models/gpt-6-luna)

**Future Plans**

Earlier versions of Sveltia CMS included DeepL integration, but we had to disable it [due to an API limitation](https://github.com/sveltia/sveltia-cms/issues/437). It may be reintroduced in the future when we find a suitable workaround. Support for a CORS proxy is being considered.

More translation services may be added in the future.

### Choosing a Service

A few notes to help you choose a service:

- NMT is specialized for translations, while LLMs are more general-purpose.
- NMT is fast, while LLMs may produce more natural, context-aware translations.
- Google and Mistral AI offer free tiers, while other services require a paid plan.
- Claude Max and Team subscriptions include [monthly API credits](https://support.claude.com/en/articles/17154008-monthly-api-credits-for-max-and-team-plans), which can be used for translation.
- With [Gemini’s free tier](https://ai.google.dev/gemini-api/docs/pricing), API input and output may be used to improve their products. As their terms state, do not send sensitive or confidential information while using the free tier. Consider using the paid plan or other services if this is a concern.
- DeepSeek may refuse to translate content on certain politically sensitive topics, since it’s required to follow local rules and regulations in China.

### Requirements

You need to obtain an API key from the translation service provider of your choice. Some services may require you to set up billing information, even for free tiers. See the instructions below for each service:

- Google Cloud Translation
  1.  Sign in or sign up for [Google Cloud](https://cloud.google.com/) and create a new project.
  1.  Enable the [Cloud Translation API](https://console.cloud.google.com/apis/library/translate.googleapis.com). It’s free up to 500,000 characters per month.
  1.  Create a [new API key](https://console.cloud.google.com/apis/api/translate.googleapis.com/credentials) and copy it.
- Google Gemini
  1.  Sign in or sign up for [Google AI Studio](https://aistudio.google.com/).
  1.  A new [API key](https://aistudio.google.com/api-keys) is created automatically for your account. Or create a new one if needed, and copy it.
- Anthropic
  1.  Sign in or sign up for [Claude Developer Platform](https://docs.claude.com/en/docs/api/overview).
  1.  Add a credit balance (minimum $5) to your account.
  1.  Create a [new API key](https://platform.claude.com/settings/keys) and copy it.
- DeepSeek
  1.  Sign in or sign up for [DeepSeek Platform](https://platform.deepseek.com/).
  1.  Add a credit balance (minimum $2) to your account.
  1.  Create a [new API key](https://platform.deepseek.com/api_keys) and copy it.
- Mistral AI
  1.  Sign in or sign up for [Mistral AI Console](https://console.mistral.ai/).
  1.  Add a credit balance if needed. The free tier is [rate limited](https://docs.mistral.ai/admin/user-management-finops/tier).
  1.  Create a [new API key](https://console.mistral.ai/home?profile_dialog=api-keys) and copy it.
- OpenAI
  1.  Sign in or sign up for [OpenAI Platform](https://platform.openai.com/) and create a new project.
  1.  Add a credit balance (minimum $5) to your account.
  1.  Create a [new API key](https://platform.openai.com/api-keys) and copy it.

#### CSP

If your site uses a Content Security Policy (CSP), you may need to update it to allow requests to translation service providers. See the [CSP documentation](https://sveltiacms.app/en/docs/security#setting-up-content-security-policy) for more details.

### Configuration

You need to enable the [i18n support](https://sveltiacms.app/en/docs/i18n) in the configuration file with multiple locales to use the translation feature.

### Using the Translation Feature

1. Create a new API key for the translation service of your choice, as described above.
1. Open an entry in Sveltia CMS.
1. Click on the Translation button on the pane header or each field, right next to the 3-dot menu.
1. Select a translation service from the dropdown menu and paste an API key when prompted. A pasted key is used right away. If you type it instead, click OK once it’s complete.
1. The field(s) will be automatically translated.

Note that the Translation button on the pane header only translates empty fields, while in-field Translation buttons override any filled text.

A few limitations apply:

- Google Cloud Translation isn’t available for a locale written in a script other than the language’s usual one, such as `sr-Latn` (Serbian in the Latin script). The service would return the text in the usual script instead.
  - The script can also be implied by the region. `sr-ME` (Serbian in Montenegro) is written in the Latin script, so it isn’t available either.
  - `pa-PK` (Punjabi in Pakistan) is translated into the Arabic script, which the service supports for Punjabi.
- An LLM can only return a limited amount of text at once. If the translation of a long text is cut off at that limit, it fails with an error rather than leaving a partial translation in the field. Try translating fields one at a time in that case.

API keys can also be provided in the Settings dialog, where the default translation service can be changed as well. API keys are stored securely in the browser’s local storage, so users don’t need to enter them every time.

**Multi-user setups**

If your CMS instance is used by multiple users, the administrator needs to distribute an API key to all users to let them use the translation feature.

Alternatively, each user can provide their own API key. However, this is not recommended for instances with non-technical end users because generating and managing API keys may be challenging for them.

### Excluding Text from Translation

If you don’t want some text to be translated, use the HTML [`translate`](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Global_attributes/translate) attribute or [`notranslate`](https://developers.google.com/search/blog/2008/10/helping-you-break-language-barrier) class:

```html
<div translate="no">...</div>
```

```html
<span class="notranslate">...</span>
```

For LLMs, you can also use the `notranslate` comment to exclude specific parts of Markdown content from translation:

```html
<!-- notranslate -->...<!-- /notranslate -->
```

```html
{/* notranslate */}...{/* /notranslate */}
```
